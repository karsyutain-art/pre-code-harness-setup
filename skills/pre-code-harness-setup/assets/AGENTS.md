## 세션 시작 시 (출근)
1. PROGRESS.md를 읽어 현재 상태 파악 (SessionStart Hook이 요약을 넣어줌 — 전체가 필요하면 파일을 직접 읽기)
2. DECISIONS.md를 읽어 중요 결정 파악. 이미 내린 결정을 뒤집어야 하면 먼저 사용자에게 묻기
3. `bash .harness/checks.sh`로 저장소가 일관된 상태인지 확인
   - 실패하면 실패 내용을 PROGRESS.md "출근 시 상태"에 적고 사용자에게 알린다 (이전부터 깨져 있던 것과 내가 깨뜨린 것을 섞지 않기 위해)
   - 사용자가 자리에 없거나 계획을 연속 실행 중이면, 실패와 무관한 작업만 진행하고 기록을 남긴다
4. PROGRESS.md의 "다음 단계"에서 이어서 진행 (활성 계획이 있으면 그 진행 기록에서 재개 지점 확인)

## 사용자에게 묻거나 직접 실행을 요청하며 멈출 때
검사가 실패한 상태에서는 Stop Hook이 끝내지 못하게 한다. 사용자의 결정·승인·직접 실행이 정말 필요하면
질문을 `.harness/state/ask-user`에 한두 줄로 적고 끝낸다. 한 번만 통과되고 모든 사용이 loop-report.md에 남는다.
고치기 어려워서 빠져나가는 용도로 쓰지 않는다.

## 세션 종료 전 (퇴근)
"퇴근"은 작업 단위가 끝났을 때, 사용자가 마무리를 요청할 때, 컨텍스트가 길어져 요약·초기화하기 전.
1. PROGRESS.md 업데이트 (한 일, 다음 단계, 막힌 것). 새로 내린 중요 결정은 DECISIONS.md에 추가
2. `.harness/checks.sh` 통과 확인 — Stop Hook이 자동으로 실행한다. 통과 못 하면 끝낼 수 없다
3. 통과한 작업만 커밋 (작업 단위별 작은 커밋, 메시지에 무엇을·왜). push는 사용자 확인 후에만

## 코드 크기와 재사용
- 소프트 리밋을 넘으면 Hook이 알려준다 (이번 변경으로 생긴 초과만): 늘어난 부분을 나눌 수 있으면 나누고, 미루면 이유를 PROGRESS.md에 남긴다. 원래부터 크던 코드를 이 김에 리팩터링하지는 않는다.
- 하드 리밋을 넘으면 `.harness/checks.sh`가 실패해 완료할 수 없다. 리밋을 피하려고 줄을 합치거나 검사를 끄지 말고 책임별로 나눈다.
- 새 함수·컴포넌트·유틸을 만들기 전에 비슷한 것이 이미 있는지 검색한다. 있으면 그것을 쓰거나 일반화한다.
- 같은 로직이 세 번째로 나오면 공통 모듈로 뽑는다.
- 기존 초과 파일(`.harness/limits-baseline.txt`)은 더 키우지 않는다. 새 코드는 별도 모듈로.

## 작업 방식
- 큰 작업은 `.harness/workflow.md`의 단계 순서를 따르고, 단계가 끝날 때마다 PROGRESS.md를 갱신한다.
- 구현 계획(task 목록)이 있으면 그 계획과 진행 기록이 task 단위 기록이다. PROGRESS.md에는 같은 내용을 반복하지 않는다.
- 기능(workflow 노드) 하나가 끝나면 `.harness/reviewer.md`의 지시로 검수를 받는다:
  Claude Code는 reviewer 서브에이전트, 그 밖의 도구는 서브에이전트가 있으면 그것으로, 없으면 새 비대화형 세션으로
  (예: `codex exec "$(cat .harness/reviewer.md)"`, `gemini -p "$(cat .harness/reviewer.md)"`). 다른 회사 모델로 검수하면 놓치는 지점이 달라 효과가 크다.
