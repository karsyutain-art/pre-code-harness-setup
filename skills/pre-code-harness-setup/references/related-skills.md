# 다른 스킬과 함께 쓸 때

이 스킬은 **환경(파일·Hook)**을 깐다. 일하는 **방법**을 정하는 스킬이 함께 설치돼 있을 수 있으니, 겹치는 부분은 새로 만들지 말고 연결한다. 세션의 스킬 목록에 실제로 있는 것만 해당한다.

| 함께 있을 수 있는 스킬 | 역할 | 이 스킬에서 할 일 |
|---|---|---|
| brainstorming (spec 작성) | 무엇을 만들지 정함 | 그 **다음**에 이 스킬을 쓴다. spec이 있으면 0단계 질문 대신 spec을 읽는다 |
| writing-plans / executing-plans / subagent-driven-development | task 단위 계획·실행, 진행 기록(ledger) | workflow.md의 구현 노드는 계획 파일을 **가리키기만** 한다. task 기록은 ledger에 맡기고 PROGRESS.md에는 활성 계획·ledger 경로만 적는다 |
| using-git-worktrees | `.worktrees/<브랜치>`에서 작업 | Hook은 worktree 안에서도 그 작업 트리를 기준으로 판정한다. 세팅을 **커밋**해 둬야 worktree에도 복사된다 |
| test-driven-development | 실패하는 테스트부터 | 그대로 쓴다. 보호하는 것은 0단계에서 합의한 **합격 기준 테스트**뿐, TDD 단위 테스트는 자유롭게 고친다 |
| verification-before-completion | "완료" 전 검증 (행동 규칙) | 완료 게이트 Hook이 같은 원칙을 **강제**한다. 검증 명령은 `.harness/checks.sh` 하나로 통일 |
| 코드 리뷰 스킬, 사용자 코딩 규칙 스킬의 검토 에이전트 | 코드 품질·정확성 | reviewer는 이들이 **보지 않는 것**만 본다 — 요구사항 누락, 테스트·보호 파일 훼손, 리밋 우회, 재사용 |
| 사용자 코딩 규칙 스킬 (린트 0건, 설계 원칙 등) | 코드 작성 규칙 | 린터 설정을 그 스킬과 **공유**한다. 리밋 수치는 이 하네스 설정 한 곳에만 둔다 |
| "필요한 곳만 고치기" 류 지침 | 변경 범위 절제 | 리밋 Hook은 **이번 변경으로 생긴** 초과만 알린다. 기존 코드를 리밋 때문에 리팩터링하게 만들지 않는다 |

권장 순서: 기획(무엇을) → **이 스킬(환경)** → 계획(어떻게) → 실행(TDD·검수) → 브랜치 마무리.

## 검수 역할 나누기

검수가 여러 겹이면 비용만 늘고 같은 지적이 반복된다.

| 검수 | 언제 | 보는 것 |
|---|---|---|
| 사용자 코딩 규칙 스킬의 검토(있으면) | 코드를 작성할 때마다 | 정확성·성능·구조·보안 |
| 코드 리뷰 스킬(있으면) | 계획의 task마다 / 브랜치 끝 | 계획·spec 대비 구현 품질 |
| **reviewer (이 하네스)** | workflow 노드(기능)가 끝날 때 | `.harness/reviewer.md`의 항목 — 하네스 관점 |

다른 검수가 없으면 reviewer가 엣지 케이스·정확성까지 함께 본다(`reviewer.md` 4번).
